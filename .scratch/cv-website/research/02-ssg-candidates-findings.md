# SSG Candidate Research — CV Website (Ticket #02)

**Date:** 2026-08-25
**Scope:** Compare Astro, Eleventy (11ty), Next.js (static export), and SvelteKit (adapter-static) for a single-page CV site deploying to GitHub Pages at the root domain (`W8bro.github.io`, no base path needed). Secondary lighter pass on Hugo, Zola, Gatsby, and a plain Vite+TS starter. Primary goal context: Tom is a beginner web developer who wants this project as a vehicle to learn TypeScript; v1 has zero interactivity but the architecture should allow adding one small interactive component later without a full rearchitect.

This document is fact-gathering only. No recommendation is made except in the explicitly-labeled non-binding section at the very end.

---

## 1. Astro

### 1.1 TypeScript support

- TypeScript is native/built-in, not a plugin: "Astro ships with built-in support for TypeScript." — [Astro Docs: TypeScript](https://docs.astro.build/en/guides/typescript/)
- `.ts`/`.tsx` files work without extra setup, and Astro starter projects include a `tsconfig.json` out of the box, extending one of three official presets (`astro/tsconfigs/base`, `strict`, `strictest`):
  ```json
  { "extends": "astro/tsconfigs/base", "include": [".astro/types.d.ts", "**/*"], "exclude": ["dist"] }
  ```
  ([Astro Docs: TypeScript](https://docs.astro.build/en/guides/typescript/))
- Component props in `.astro` files are typed via a `Props` interface declared in the component's frontmatter script block, e.g. `interface Props { name: string; greeting?: string; }` — the docs instruct to "add a TypeScript `Props` interface to your component frontmatter," and the official VS Code extension recognizes this pattern for editor tooling. ([Astro Docs: TypeScript](https://docs.astro.build/en/guides/typescript/))
- The Astro config file itself can be authored in TypeScript (`astro.config.ts`) for type-safe configuration. ([Astro Docs: TypeScript](https://docs.astro.build/en/guides/typescript/), cross-referencing [Configuring Astro](https://docs.astro.build/en/guides/configuring-astro/))
- Type checking is not run by the dev server; a beginner must run `astro check` (or wire it into the build script) to catch type errors before deploy. ([Astro Docs: TypeScript](https://docs.astro.build/en/guides/typescript/))
- Client-side `<script>` tags inside `.astro` components are TypeScript by default: "All scripts are TypeScript by default," with automatic import bundling and `type="module"` handling. This means plain interactivity code (not just framework components) is typed with zero config. ([Astro Docs: Client-side Scripts](https://docs.astro.build/en/guides/client-side-scripts/))

### 2. Adding interactivity later

- Astro is fundamentally islands architecture: components render to static HTML/CSS by default, "automatically removing client-side JavaScript." Interactivity is opt-in per component via a `client:*` directive. ([Astro Docs: Islands](https://docs.astro.build/en/concepts/islands/))
- To add a theme toggle later, a beginner drops in a component and adds a directive, e.g. `<ThemeToggle client:load />`. Available directives include `client:load` (hydrate immediately), `client:idle` (hydrate when browser is idle), and `client:visible` (hydrate when scrolled into view). ([Astro Docs: Islands](https://docs.astro.build/en/concepts/islands/))
- Astro also supports zero-framework interactivity: a plain `<script>` tag (TypeScript by default, as above) inside an `.astro` file using `addEventListener`/DOM APIs — no islands, no UI framework needed at all for something as small as a theme toggle. ([Astro Docs: Client-side Scripts](https://docs.astro.build/en/guides/client-side-scripts/))
- What a beginner starting from a pure-static v1 would need to learn to add one interactive island later: (a) nothing new, if using the `<script lang="ts">`-in-`.astro`-file approach — this requires no new mental model beyond DOM APIs; or (b) if they want a component-based approach (e.g. a Preact/React/Svelte/Vue toggle component), they'd additionally install a UI-framework integration and learn the `client:*` directive vocabulary and that framework's component syntax. Either path is additive — no rearchitecture of the existing static pages is implied by Astro's model.

### 3. GitHub Pages deploy story

- Astro maintains an official first-party GitHub Action: "Astro maintains an official Astro GitHub Action to deploy your project to GitHub Pages with very little configuration," referenced as `withastro/action@v6` in the workflow. ([Astro Docs: Deploy to GitHub Pages](https://docs.astro.build/en/guides/deploy/github/); action repo: [withastro/action](https://github.com/withastro/action))
- Required config: `site` must be set to the GitHub Pages URL (for a user/org page like `W8bro.github.io`, this is `https://<username>.github.io`). `base` is "usually required" to match the repo name for project-page repos, but is explicitly unnecessary for the special `<username>.github.io` user-page repo pattern — which is exactly Tom's case. ([Astro Docs: Deploy to GitHub Pages](https://docs.astro.build/en/guides/deploy/github/))
- Gotcha (not applicable here, but noted): if `base` is set, all internal links must be prefixed with it — irrelevant for `W8bro.github.io` since no `base` is needed.
- Gotcha (lockfile): the official action "scans for a lockfile to detect your preferred package manager," so the lockfile must be committed. ([Astro Docs: Deploy to GitHub Pages](https://docs.astro.build/en/guides/deploy/github/))
- `.nojekyll` gotcha: the official Astro deploy doc page itself does not mention `.nojekyll`, but community reports (secondary corroboration) confirm Astro's build output includes a `_astro/` asset directory, which GitHub's default Jekyll processing ignores (any `_`-prefixed folder), breaking CSS/JS on Pages unless a `.nojekyll` file is present at the site root. This is a live, filed GitHub issue against Astro. ([GitHub issue: withastro/astro#14247 "_astro folder in dist/ is ignored by Github Pages"](https://github.com/withastro/astro/issues/14247); secondary: [seanmcp.com — Fix missing Astro files on GitHub Pages](https://www.seanmcp.com/articles/fix-missing-astro-files-on-github-pages/)). Whether the official `withastro/action` inserts `.nojekyll` automatically was not confirmed from primary sources in this pass — worth a direct check of the action's source before relying on it.

### 4. Beginner learning curve

- Default Astro authoring is close to plain HTML with a frontmatter script block — `.astro` files are HTML-first with a JS/TS "fence" at the top, no required client-side routing or hydration concepts for a purely static site.
- A beginner learning TS alongside Astro is mostly learning: (a) how to write a `Props` interface for typed component data, and (b) if/when they add interactivity, the `client:*` directive vocabulary. No requirement to learn a client-side router or global hydration model up front, since v1 needs none of it. The islands concept only needs to be learned at the point interactivity is actually added — consistent with the "no rearchitect" goal.

## 2. Eleventy (11ty)

### 1. TypeScript support

- As of Eleventy v3.0.0, TypeScript is described as a first-party, built-in capability (not a plugin), enabled via one of two mechanisms:
  1. **Native Node.js type stripping** (Node 22.6+): "Here we use Node.js' type stripping feature (available in Node 22.6+) to process `*.11ty.ts` TypeScript files," registered via `eleventyConfig.addExtension("11ty.ts", { key: "11ty.js" }); eleventyConfig.addTemplateFormats("11ty.ts");` ([11ty Docs: TypeScript](https://www.11ty.dev/docs/languages/typescript/))
  2. **The `tsx` package**, which requires the project to be ESM (`"type": "module"` in `package.json`, or a `.mjs` config file). ([11ty Docs: TypeScript](https://www.11ty.dev/docs/languages/typescript/))
- The config file itself can be TypeScript: `npx @11ty/eleventy --config=eleventy.config.ts`. ([11ty Docs: TypeScript](https://www.11ty.dev/docs/languages/typescript/))
- Template files use a `.11ty.ts` or `.11ty.tsx` extension (JS-as-template-language, i.e. "template files" that export render functions/data, not a `.astro`/`.svelte`-style single-file component format). Front matter is explicitly not supported in TS template files — "Use a `data` export instead." ([11ty Docs: TypeScript](https://www.11ty.dev/docs/languages/typescript/))
- Eleventy's general philosophy is template-language-agnostic — it natively supports Markdown, Liquid, Nunjucks, HTML, WebC, JS, and others rather than mandating one component model. ([11ty Docs: Getting Started](https://www.11ty.dev/docs/))
- Important nuance for Tom's use case: Eleventy's TS support is about writing *config and page templates* in TS (i.e. the site-generation logic), not about typed "component props" the way Astro/Svelte/Next do — because Eleventy doesn't have a single-file component model with a props contract. If most of the CV page is static HTML/Nunjucks/Markdown, there may be very little actual TypeScript surface area day-to-day beyond the `eleventy.config.ts` file and any small client-side script.

### 2. Adding interactivity later

- Eleventy ships zero client-side JS by default and has no islands/hydration model at all — it is a plain templating pipeline that emits static HTML. Adding "one small interactive component" later means writing a plain `<script>` tag with vanilla (or TypeScript-compiled-to-JS) code and linking it from the page, exactly like traditional static HTML — there is no framework-level concept to learn (no directives, no hydration).
- This is architecturally the simplest of the four for "add later without rearchitect," because there is no architecture to disturb: static HTML output today, and a `<script src="theme-toggle.js">` (built from a `.ts` file via whatever bundler Eleventy is configured with, e.g. esbuild/Vite plugins) added later, is a pure addition.
- Caveat: because Eleventy doesn't prescribe a JS bundler, a beginner adding real TypeScript-authored client-side interactivity would need to set up their own build step (e.g. an 11ty plugin for esbuild/Vite, or a simple manual `tsc` compile step) — this is not automatic the way Astro's client scripts or Vite-backed frameworks are. This is the one place Eleventy asks more manual setup than the other three candidates.

### 3. GitHub Pages deploy story

- Eleventy's official docs describe a GitHub Actions deployment recipe: create `.github/workflows/deploy-gh-pages.yml` (referencing the `eleventy-base-blog` sample workflow), then under repo Settings → Pages → Build and deployment → Source, select "GitHub Actions." ([11ty Docs: Deployment](https://www.11ty.dev/docs/deployment/))
- Default output directory is `_site` (configurable). The docs state you "upload your Eleventy output directory (defaults to `_site`) to the host manually" for non-Action-based deploys. ([11ty Docs: Deployment](https://www.11ty.dev/docs/deployment/))
- Path prefix: for project repos (`username.github.io/repo-name`) add `--pathprefix=/YOUR_REPO_NAME/` to the build script; explicitly **remove** `--pathprefix` when deploying to `username.github.io` root or a custom domain — this matches Tom's case exactly (root user-page repo, no prefix needed). ([11ty Docs: Deployment](https://www.11ty.dev/docs/deployment/))
- Build caching: the docs mention using GitHub's `cache` action to persist Eleventy's `.cache` folder between builds (relevant for image processing, less relevant for a simple CV site). ([11ty Docs: Deployment](https://www.11ty.dev/docs/deployment/))
- `.nojekyll` gotcha: the official deployment doc excerpt fetched here did not explicitly surface a `.nojekyll` instruction, but this is a well-documented general GitHub Pages gotcha (any output folder/file starting with `_` — Eleventy's default `_site` output *directory name* itself is not the issue since that's the source-to-host mapping, but `_includes`/other underscore-prefixed asset paths inside the output can be silently dropped by Jekyll) — corroborated by multiple secondary sources describing `.nojekyll` as "essential for Eleventy projects on GitHub Pages" to stop Jekyll processing. ([Secondary: Ian Wootten — "How to Use Underscores with GitHub Pages"](https://www.ianwootten.co.uk/2022/11/08/how-to-use-underscores-with-github-pages/); secondary: dev.to — "How to deploy Eleventy to GitHub Pages with GitHub Actions"](https://dev.to/sophiabrandt/how-to-deploy-eleventy-to-github-pages-with-github-actions-0))

### 4. Beginner learning curve

- Eleventy is the closest of the four to plain HTML/templating: no required component model, no client-side router, no hydration concept. A beginner writes Nunjucks/Markdown/HTML templates and Eleventy stamps out static pages.
- Learning TS alongside Eleventy is more decoupled from "learning the framework" than with Astro/Next/SvelteKit, because Eleventy's TS support applies to the config/build logic and to your own hand-written client scripts, not to a typed component-props system. This could be a pro (less to learn at once) or a con (less structured practice writing typed interfaces) depending on how Tom wants to learn TS.

## 3. Next.js (Static Export, `output: export`)

### 1. TypeScript support

- TypeScript is built-in/first-party: "Next.js comes with built-in TypeScript, automatically installing the necessary packages and configuring the proper settings when you create a new project with `create-next-app`." ([Next.js Docs: TypeScript](https://nextjs.org/docs/app/api-reference/config/typescript))
- Adding TS to an existing JS project is as simple as renaming a file to `.ts`/`.tsx` and running `next dev`/`next build`, which auto-installs deps and generates `tsconfig.json`. ([Next.js Docs: TypeScript](https://nextjs.org/docs/app/api-reference/config/typescript))
- The config file can be TypeScript (`next.config.ts`), typed via `import type { NextConfig } from 'next'`. ([Next.js Docs: TypeScript](https://nextjs.org/docs/app/api-reference/config/typescript))
- Page/component props in the App Router are typed with normal TypeScript/React idioms (props interfaces on function components) plus Next-generated helpers: `PageProps`, `LayoutProps`, `RouteContext` are auto-generated global type helpers (no import needed) for route-aware typing. ([Next.js Docs: TypeScript](https://nextjs.org/docs/app/api-reference/config/typescript))
- Next.js auto-generates a `next-env.d.ts` (must stay in `tsconfig.json`'s `include`, and per the docs should be gitignored / not hand-edited) and, if `typedRoutes` is enabled, statically-typed `<Link href>` checking against real app routes. ([Next.js Docs: TypeScript](https://nextjs.org/docs/app/api-reference/config/typescript))
- `next build` fails the production build on TypeScript errors by default (can be disabled via `typescript.ignoreBuildErrors`, discouraged). ([Next.js Docs: TypeScript](https://nextjs.org/docs/app/api-reference/config/typescript))
- Note: this is the deepest, most "framework-opinionated" TypeScript integration of the four — it comes bundled with React's JSX/prop-typing model, not just "TS in template files."

### 2. Adding interactivity later

- Next.js's interactivity model is React's Client/Server Component split, not islands: any component needs `'use client'` at the top of the file to become interactive/hydrated in the browser; everything else defaults to Server Components (which, under static export, are just resolved to static HTML at build time). ([Next.js Docs: Static Exports](https://nextjs.org/docs/app/guides/static-exports) — shows both a Server Component data-fetch example and a `'use client'` example using `useSWR`)
- To add a theme toggle later: create a small component file, add `'use client'` at the top, use React state/hooks (`useState`, `useEffect` for browser-only APIs like `window`/`localStorage` since these aren't available during the static build). The docs explicitly flag this: "Because Web APIs like `window`, `localStorage`, and `navigator` are not available on the server, you need to safely access these APIs only when running in the browser" (typically inside `useEffect`). ([Next.js Docs: Static Exports](https://nextjs.org/docs/app/guides/static-exports))
- What a beginner would need to newly learn versus a pure-static v1: React itself (JSX, components, hooks, `useState`/`useEffect`), the Server/Client Component boundary and the `'use client'` directive, and the browser-API-timing gotcha above. This is meaningfully more conceptual surface than Astro's islands or Eleventy's plain `<script>` approach, because a beginner must understand React's whole component/hook model just to add one small piece of interactivity, even though the rest of the site stays static.

### 3. GitHub Pages deploy story

- Enabling static export: set `output: 'export'` in `next.config.js`/`.ts`. Optional related settings in the same block: `trailingSlash` (changes `/me` → `/me/`, emits `/me.html` → `/me/index.html`), `skipTrailingSlashRedirect`, and `distDir` (rename `out` → e.g. `dist`). Default output directory is `out/`. ([Next.js Docs: Static Exports](https://nextjs.org/docs/app/guides/static-exports))
- Official GitHub Pages deploy path: "To deploy to GitHub Pages, use our template to create a new project or as a reference for configuring an existing project," linking to the official template repo. ([Next.js Docs: Static Exports](https://nextjs.org/docs/app/guides/static-exports); template: [github.com/nextjs/deploy-github-pages](https://github.com/nextjs/deploy-github-pages))
- Fetched the template's actual workflow YAML directly: it uses the standard modern GitHub Pages Actions stack — `actions/checkout`, `pnpm/action-setup`, `actions/setup-node`, `actions/configure-pages` (which exposes a `base_path` output consumed as `PAGES_BASE_PATH` env var during `pnpm run build`), `actions/cache` for `.next/cache`, `actions/upload-pages-artifact@v3` pointed at `./out`, and finally `actions/deploy-pages@v4`. No `.nojekyll` step appears in this workflow — because `actions/deploy-pages` deploys the uploaded artifact directly via the Pages API/CDN rather than committing to a branch that GitHub's legacy Jekyll pipeline would process, so `.nojekyll` is not needed for this "GitHub Actions" deployment source (as opposed to the older gh-pages-branch method). ([github.com/nextjs/deploy-github-pages, `.github/workflows/deploy.yml`](https://github.com/nextjs/deploy-github-pages))
- Static-export unsupported features list, directly from the docs — relevant to know even though a CV site is unlikely to need them: Dynamic Routes with `dynamicParams: true` or without `generateStaticParams()`, Route Handlers relying on `Request`, Cookies, Rewrites, Redirects, Headers, Proxy/middleware, Incremental Static Regeneration, default-loader Image Optimization (`next/image` needs a custom loader, e.g. pointed at Cloudinary, or must be avoided), Draft Mode, Server Actions, Intercepting Routes. ([Next.js Docs: Static Exports](https://nextjs.org/docs/app/guides/static-exports))
- Version history note: `next export` (the old CLI command) was removed in v14.0.0 in favor of `output: 'export'` — so any tutorial referencing `next export` as a command is stale. ([Next.js Docs: Static Exports](https://nextjs.org/docs/app/guides/static-exports))

### 4. Beginner learning curve

- Highest conceptual overhead of the four for a total beginner: on top of TypeScript, Next.js requires learning React (components, JSX, hooks) and Next's own App Router conventions (file-based routing via `app/`, Server vs. Client Components, the static-export constraint list above). Even a "zero interactivity" v1 CV page is written as a React component tree, not plain HTML.
- The App Router's "enhanced type safety" and end-to-end typing features (`PageProps`, typed routes, etc.) are genuinely nice once learned, but they are additional vocabulary on top of both TS and React fundamentals — a lot to absorb simultaneously for someone who is a beginner at web dev in general.

## 4. SvelteKit (adapter-static)

### 1. TypeScript support

- TypeScript is offered as a first-class scaffolding option: "The easiest way to get started is scaffolding a new SvelteKit project by typing `npm create svelte@latest`... choosing the TypeScript option," which sets up a `tsconfig.json` (or `jsconfig.json` if the user opts for type-checked `.js` instead). ([Svelte community search summary citing SvelteKit docs: Project structure / Getting started](https://svelte.dev/docs/kit/project-structure))
- SvelteKit generates and maintains its own `.svelte-kit/tsconfig.json`, which the project's own `tsconfig.json` is expected to `extend` rather than replace — the docs note this generated config sets compiler options like `verbatimModuleSyntax: true` and `isolatedModules: true`. ([Svelte docs, per search of svelte.dev/docs/kit/types and /configuration](https://svelte.dev/docs/kit/types))
- Default project structure: `src/routes` (pages, required), `src/lib` (importable via the `$lib` alias), `src/lib/server` (server-only code), `static/` (raw static assets) — "Everything except `src/routes` and `src/app.html` is optional." ([Svelte docs: Project structure](https://svelte.dev/docs/kit/project-structure))
- In Svelte 5 specifically (the current version), TypeScript in `.svelte` files is native for type-only syntax via `<script lang="ts">` — "all features that just disappear when transpiling to JavaScript, such as type annotations or interface declarations" work with no preprocessor. Features that require actual code generation (e.g. enums, parameter-property-style class shortcuts) need a preprocessor (`vitePreprocess`). Component props are typed via the `$props()` rune destructured against a typed shape, e.g. `let { requiredProperty, optionalProperty }: Props = $props();`, and generic component relationships are declared via a `generics` attribute on the `<script>` tag. ([Svelte Docs: TypeScript](https://svelte.dev/docs/svelte/typescript))
- Net effect: TS support is native at the language level (Svelte 5 compiles type syntax away directly) and first-party at the tooling level (scaffolding, generated tsconfig, VS Code extension) — no bolt-on plugin required for typical use.

### 2. Adding interactivity later

- SvelteKit does not use an islands/partial-hydration model the way Astro does — a SvelteKit app is a full client-side app framework: by default every page can be server-rendered (or, under `adapter-static`, prerendered to static HTML) *and* subsequently hydrated for client-side navigation, unless explicitly disabled.
- The relevant mechanism for keeping a project as inert static HTML by default and adding interactivity later is Svelte's own component reactivity (not a separate directive system): a beginner just writes a `.svelte` component (e.g. `ThemeToggle.svelte`) with a `<script>` block using Svelte 5 runes (`$state`, etc.) and drops it into a page — it hydrates automatically as part of normal SvelteKit page hydration, no special directive needed (unlike Astro's `client:*`).
- For a purely static, near-zero-JS v1, `adapter-static` with `export const prerender = true` produces static HTML with client-side hydration JS still shipped for that page (SvelteKit always hydrates prerendered pages by default unless `csr` is explicitly disabled) — so "zero interactivity" in SvelteKit still means a JS runtime is present on the page, just idle, whereas Astro can ship literally zero JS by default. A beginner wanting truly zero JS for v1 would need to explicitly set `export const csr = false` in a `+page.js`/`+layout.js` for the relevant route, and would need to re-enable/scope `csr` back on for interactivity to work when they add the toggle later.
- SvelteKit also documents a fully client-only "single-page app" mode (`export const ssr = false; export const csr = true; export const prerender = false;`) via `adapter-static`'s `fallback` option (e.g. `adapter({ fallback: '200.html' })`), but this is a different, more SPA-oriented mode than what a static CV site with prerendering needs — worth knowing it exists but likely not the right mode here. ([Svelte Docs: Single-page apps](https://svelte.dev/docs/kit/single-page-apps); adapter config: [Svelte Docs: adapter-static](https://svelte.dev/docs/kit/adapter-static))
- What a beginner has to newly learn to add one interactive component later, starting from static v1: Svelte's component/reactivity model (runes: `$state`, `$props`, `$effect`), and — only if they had turned CSR off for a fully JS-free v1 — how to re-enable client-side JS for that specific route. No routing concepts need to be learned for a single-page CV site since there's only one route.

### 3. GitHub Pages deploy story

- No dedicated single-command official GitHub Action equivalent to `withastro/action`; the official path is the general-purpose `@sveltejs/adapter-static` package plus a GitHub Actions workflow the docs walk through. Repo: [sveltejs/kit — packages/adapter-static](https://github.com/sveltejs/kit/tree/main/packages/adapter-static); docs: [Svelte Docs: adapter-static](https://svelte.dev/docs/kit/adapter-static).
- Configuration: install `@sveltejs/adapter-static`, set it in `svelte.config.js`, and set `export const prerender = true` in the root `+layout`. Output directories default to `build` (configurable via `pages`/`assets` options). `strict: true` by default validates that all pages were actually prerendered (fails the build otherwise) — a useful safety net for a static CV site. `fallback` (e.g. `'200.html'`/`'404.html'`) is for SPA-style setups, not needed for a fully-prerendered static site. `precompress` can pre-generate `.br`/`.gz` files. ([Svelte Docs: adapter-static](https://svelte.dev/docs/kit/adapter-static))
- For project-repos (not the `username.github.io` root case), `config.kit.paths.base` must be set to the repo name — explicitly **not needed** for Tom's `W8bro.github.io` root-domain case, matching the other three frameworks.
- `.nojekyll` gotcha: the docs require "an empty `.nojekyll` file in your static folder" to stop GitHub's Jekyll from mangling the site, and separately warn that if `.nojekyll` is not used, the default `_app` output directory name (leading underscore) will be silently dropped by Jekyll — so either add `.nojekyll` or rename the app dir away from a leading underscore. ([Svelte Docs: adapter-static](https://svelte.dev/docs/kit/adapter-static), corroborated by community writeups e.g. [Stanislav Khromov — "The missing guide to understanding adapter-static in SvelteKit"](https://khromov.se/the-missing-guide-to-understanding-adapter-static-in-sveltekit/))
- `trailingSlash`: the docs flag that "you must ensure SvelteKit's `trailingSlash` option is set appropriately for your environment" — GitHub Pages' static file server behavior around directory URLs needs this considered, similar in spirit to Next.js's equivalent option.

### 4. Beginner learning curve

- Middle-of-the-pack overhead: SvelteKit's component syntax (`.svelte` files: `<script>`, markup, `<style>` in one file) is simpler to read than JSX/React for a beginner, and Svelte 5's runes (`$state`, `$props`) are a comparatively small, explicit vocabulary.
- However, SvelteKit is a full application framework with routing, load functions, and SSR/prerendering/CSR toggles baked in from the start — even a one-page static site is technically "a SvelteKit app with one route," so the beginner is exposed to the framework's fuller conceptual surface (file-based routing conventions, `+page.svelte`/`+layout.svelte` naming, the prerender/ssr/csr export flags) even though a single CV page won't exercise most of it. This is more upfront structure than Eleventy or a plain Vite+TS page, and roughly comparable to (arguably a bit less than) Next.js, but without React's hook/JSX model layered on top.

## 5. Other candidates considered (lighter pass)

- **Hugo** — Written in Go, not TypeScript; templates use Go's `html/template` syntax, not TS/JS. Hugo does have a JS/TS asset pipeline (its bundler can "transpile TypeScript and JSX to JavaScript, bundle, tree shake, minify... and perform SRI hashing" for asset files), but the site-generation/templating layer itself has no TypeScript story — TS would only ever touch client-side script assets, not the templates or config. Extremely fast builds, but doesn't serve Tom's stated goal of learning TypeScript through the project's core authoring workflow. (Secondary corroboration: [Hygraph — Top 12 SSGs 2026](https://hygraph.com/blog/top-12-ssgs); [talos.tools — Best SSGs 2026](https://talos.tools/blog/best-static-site-generators-2026))
- **Zola** — Written in Rust, single static binary, uses the Tera template language (Jinja2-like), with no TypeScript integration at all — irrelevant to a TypeScript-learning goal. ([getzola.org](https://www.getzola.org/); GitHub: [getzola/zola](https://github.com/getzola/zola))
- **Gatsby** — React + GraphQL-based SSG; as of 2026 it is widely described as effectively in maintenance mode: Netlify acquired Gatsby Inc. in Feb 2023, the last major release (Gatsby 5) shipped Nov 2022 (5.14.0 in Nov 2024), and much of its plugin ecosystem is unmaintained. Deploy story is the older manual `gatsby build` → `public/` → push to `gh-pages` branch pattern rather than a modern first-party Actions-based flow. Not a good pick for a new 2026 project given the maintenance signal, despite having real TypeScript support via React. (Secondary: [Wikipedia — Gatsby (software)](https://en.wikipedia.org/wiki/Gatsby_(software)); [gatsby.deployment.to — How to Deploy a Gatsby Site (2026)](https://gatsby.deployment.to/))
- **Plain Vite + TypeScript (`vanilla-ts` template)** — No framework/SSG at all; `npm create vite@latest -- --template vanilla-ts` scaffolds a minimal TypeScript project with `index.html` as the entry point. TypeScript is first-class/native to Vite's tooling. Vite supports multi-page apps via multiple HTML entry points, but there is no content templating, no component model, and no built-in "SSG" concept — a CV site here would be closer to hand-written HTML/CSS with a `<script type="module" src="main.ts">`, using Vite purely as a dev server/bundler. This is architecturally the simplest possible option and arguably the most "TypeScript-forward" in the sense that essentially all the logic a beginner writes would be TS, but it offers the least structure/scaffolding of any candidate. ([Vite Guide](https://vite.dev/guide/))

## If I had to guess (non-binding)

**This is NOT a final decision.** Ticket #03 will have a human resolve the final SSG choice with Tom directly, weighing the tradeoffs above against his actual preferences and goals. The following is a tentative, non-binding lean based only on the research above.

Given the stated priorities — Tom is a *beginner* using this project primarily *to learn TypeScript*, v1 has *zero interactivity*, and the architecture should allow *one small interactive component later without a rearchitect* — **Astro** looks like the strongest fit among the four on paper: its TypeScript integration touches every layer a beginner would actually write (config, component props, and even plain `<script>` blocks are TS by default with zero setup), its default output is genuinely static HTML with no framework runtime shipped until interactivity is deliberately opted into, and adding a single small interactive widget later (a theme toggle) is a same-file, additive change — either a typed `<script>` block or a single `client:*`-directive island — that doesn't require learning routing, hydration-by-default, or a full UI framework's hook model just to get there. Eleventy is close behind and arguably even *simpler* structurally, but its TypeScript story lives mostly in config/build logic rather than in typed component authoring, which may give Tom less hands-on TS practice day-to-day. Next.js and SvelteKit both bring more architecture (React's component/hook model, or SvelteKit's full routing/ssr/csr framework) than a one-page static CV strictly needs, which is a real cost for a beginner even though both are capable, well-documented choices.

This lean should be treated as a starting hypothesis for ticket #03's discussion, not a settled answer.
