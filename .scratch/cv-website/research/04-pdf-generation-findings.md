# Research: Generating a PDF from the built static CV site in GitHub Actions

**Question:** What are the realistic approaches for auto-generating a downloadable PDF from the built static HTML site, as a step in the existing GitHub Actions → GitHub Pages pipeline, so the PDF can't drift out of sync with the site content?

**Scope note:** This is research only. No approach is recommended over another here — that decision is deferred to a separate ticket. A non-binding personal lean is given at the very end, clearly labeled as a guess.

---

## 1. Headless-browser print-to-PDF via Puppeteer

Puppeteer is a Node.js library that drives headless Chrome/Chromium over the DevTools protocol. Its `page.pdf()` method prints the currently loaded page to a PDF using Chromium's print engine.

- **What it does by default:** `page.pdf()` "generates a PDF document from a webpage, applying the `print` CSS media type by default" — [pptr.dev/api/puppeteer.page.pdf](https://pptr.dev/api/puppeteer.page.pdf). To render as it would appear on-screen instead, you must explicitly call `page.emulateMediaType('screen')` before `page.pdf()` — same source.
- **Print stylesheet needed?** Not strictly required to get *a* PDF — it will capture the rendered page. But because Chromium applies `@media print` styles by default, a page with no print stylesheet may render with browser-default print behavior (e.g., altered colors for ink-saving). The docs specifically flag that "`page.pdf()` generates a pdf with modified colors for printing" and that the `-webkit-print-color-adjust` CSS property is the escape hatch to force exact colors — [pptr.dev/api/puppeteer.page.pdf](https://pptr.dev/api/puppeteer.page.pdf). So: works without a print stylesheet, but a print stylesheet gives control over layout/colors/page breaks rather than leaving it to Chromium defaults.
- **Setup complexity for a beginner:** Install the `puppeteer` npm package (as opposed to `puppeteer-core`); by default this bundles/downloads a matching Chromium build the first time it's installed. Write a short Node script that launches the browser, opens the built HTML file (e.g., via `file://` path or a local static server), and calls `page.pdf({ path: ... })`.
- **CI runtime / install cost:**
  - Chromium download size on install is roughly 170–280 MB depending on OS (macOS ~170MB, Windows ~280MB, Debian/Ubuntu ~282MB) — reported via community sources referencing Puppeteer's own install behavior (search aggregation, not a single canonical page with a size table; treat as approximate) — see [puppeteer/puppeteer issue #3027](https://github.com/puppeteer/puppeteer/issues/3027) discussion and related npm packaging notes.
  - Puppeteer's own troubleshooting docs describe the browser cache location (`~/.cache/puppeteer` since v19) and how to configure it via `PUPPETEER_CACHE_DIR`, and note that some package managers disable postinstall scripts (so `npx puppeteer browsers install` may need to be run explicitly) — [pptr.dev/troubleshooting](https://pptr.dev/troubleshooting).
  - Linux CI environments need extra system libraries (e.g. `libgtk-3-0`, `libnss3`, `libxss1`, etc. on Debian/Ubuntu) — [pptr.dev/troubleshooting](https://pptr.dev/troubleshooting).
  - GitHub-hosted Ubuntu runners already ship a preinstalled Google Chrome and Chromium build (e.g. Ubuntu 24.04 image lists "Google Chrome 151.0.7922.137" and "Chromium 151.0.7922.0" plus matching webdrivers and Selenium server) — [actions/runner-images Ubuntu2404-Readme.md](https://github.com/actions/runner-images/blob/main/images/ubuntu/Ubuntu2404-Readme.md). Puppeteer's default install still downloads its own pinned Chromium build rather than relying on that system browser, since it's tested against a specific bundled version — general Puppeteer install behavior per [pptr.dev/troubleshooting](https://pptr.dev/troubleshooting).
  - No official Puppeteer statement on `actions/cache` was found either recommending or discouraging caching the browser binary between CI runs; the troubleshooting docs focus on cache *location*, not whether to persist it across runs — [pptr.dev/troubleshooting](https://pptr.dev/troubleshooting).
  - Sandbox note: the docs recommend against blanket `--no-sandbox` where avoidable, and flag that AppArmor policies on Ubuntu 23.10+ can block "Chrome for Testing," requiring a documented workaround — [pptr.dev/troubleshooting](https://pptr.dev/troubleshooting).

## 2. Headless-browser print-to-PDF via Playwright

Playwright (Microsoft) is comparable in concept to Puppeteer but manages three browser engines. Its `page.pdf()` API is Chromium-only.

- **Browser restriction:** `page.pdf()` is only supported in headless Chromium — Firefox and WebKit throw an error if called — confirmed via a Playwright maintainer bug-report thread: [microsoft/playwright-python issue #2909](https://github.com/microsoft/playwright-python/issues/2909). (The official API reference page did not spell this restriction out explicitly in the fetched excerpt, but the linked options list — paper format, margins, headers/footers with `date`/`title`/`url`/`pageNumber`/`totalPages` template classes, landscape, scale 0.1–2.0, page ranges, background graphics, "tagged PDF," CSS page-size preference — comes from [playwright.dev/docs/api/class-page#page-pdf](https://playwright.dev/docs/api/class-page).)
- **Print stylesheet needed?** Same story as Puppeteer: not required to get output, but the API reference explicitly frames PDF output as governed by `@media print`/`@page` rules, and community guidance built on the official docs states plainly that "PDFs rely on `@media print` and `@page` rules" and that print CSS "should be treated as part of the product, not as an afterthought" for anything beyond a single simple page — [Checkly Docs, citing Playwright's API](https://www.checklyhq.com/docs/learn/playwright/generating-pdfs/). As with Puppeteer, default colors are print-adjusted; `-webkit-print-color-adjust` is the same override — [playwright.dev/docs/api/class-page](https://playwright.dev/docs/api/class-page).
- **Setup complexity for a beginner:** Install the `playwright` (or `@playwright/test`) npm package, then run `npx playwright install` (optionally `--with-deps` on Linux to also install OS-level dependencies) to fetch browser binaries, then write a short script/test that opens the built HTML and calls `page.pdf()`.
- **CI runtime / install cost:**
  - The official CI guide's example workflow uses `npx playwright install --with-deps` as the standard installation step in GitHub Actions — [playwright.dev/docs/ci-intro](https://playwright.dev/docs/ci-intro).
  - No first-party "Playwright GitHub Action" wrapping this was found on the official docs pages fetched — the recommended pattern is plain `npx` commands inside a normal `actions/checkout` + `actions/setup-node` workflow, not a dedicated Marketplace action — [playwright.dev/docs/ci-intro](https://playwright.dev/docs/ci-intro).
  - Disk usage for installed browsers: Playwright's own docs give an example breakdown of "281M chromium-XXXXXX, 187M firefox-XXXX, 180M webkit-XXXX," i.e. a few hundred MB total when all three engines are installed — [playwright.dev/docs/browsers](https://playwright.dev/docs/browsers). Installing only Chromium (sufficient for `page.pdf()`) would be a fraction of that.
  - **Caching guidance is explicit and primary-sourced:** Playwright's official CI docs state caching browser binaries between CI runs is **not recommended**, because "the amount of time it takes to restore the cache is comparable to the time it takes to download the binaries," and on Linux the OS-level dependencies still need installing regardless of whether the browser binary itself was restored from cache — [playwright.dev/docs/ci](https://playwright.dev/docs/ci). If caching is done anyway, the docs say to key the cache on the Playwright version and target the browser-binary directories described at [playwright.dev/docs/browsers#managing-browser-binaries](https://playwright.dev/docs/browsers).
  - The install location is configurable via `PLAYWRIGHT_BROWSERS_PATH`, and Playwright performs its own garbage collection of unused browser versions as the package is upgraded — [playwright.dev/docs/browsers](https://playwright.dev/docs/browsers).
  - As with Puppeteer, GitHub's own Ubuntu runner images already ship a system Chrome/Chromium, but Playwright's supported workflow installs its own pinned build via `npx playwright install` rather than depending on that — [playwright.dev/docs/ci-intro](https://playwright.dev/docs/ci-intro); [actions/runner-images Ubuntu2404-Readme.md](https://github.com/actions/runner-images/blob/main/images/ubuntu/Ubuntu2404-Readme.md).

## 3. Existing GitHub Actions that wrap this

Several third-party Marketplace actions exist that wrap Puppeteer (no Playwright-based or wkhtmltopdf-based Marketplace action was found in this search) for HTML→PDF conversion. None showed a "verified creator" badge — that badge is generally reserved for actions published by organizations that have completed GitHub's separate publisher-verification process, which small personal-repo actions don't have.

- **[HTML to PDF Action (LukaszLapaj)](https://github.com/marketplace/actions/html-to-pdf-action):** Wraps Puppeteer directly — its `pdfOptions` input is explicitly Puppeteer's own `page.pdf()` options object passed through. Maintenance signals: only 3 stars, latest tag `2.0.0`, third-party/non-verified publisher, not GitHub-certified.
- **[Webpage to PDF (misaelnieto)](https://github.com/marketplace/actions/webpage-to-pdf):** Takes a URL as input rather than a local file, also Puppeteer-based under the hood ("internally uses Puppeteer... to get the page and render it to print it to PDF"). Supports toggling screen vs. print media emulation. Maintenance signals: 14 stars, ~3 contributors, latest version `v0.3.1`, explicitly marked "not certified by GitHub."
- **[ntdesmond/html2pdf-action](https://github.com/ntdesmond/html2pdf-action):** Also Puppeteer-based, converts local or remote HTML to PDF, exposes Puppeteer's `PDFOptions`. Maintenance signals: 0 stars, 33 commits, no visible release date in the repo view checked.
- Other listings surfaced in the Marketplace search but not individually verified here: "HTML to PDF" (fifsky), "HTML to PDF (supports any js framework)," "Create PDF," "Generate PDF Action," "web_to_pdf_action" — general search results indicate these cluster around the same pattern (thin wrappers around Puppeteer's `page.pdf()`), per Marketplace search results for `html to pdf action puppeteer`.
- **General pattern observed:** every Puppeteer-wrapping action found is a small, low-star, single/few-maintainer community project, not a GitHub-verified or heavily-adopted action. Using one of these means depending on someone else's Docker image / npm dependency freshness rather than pinning Puppeteer or Playwright directly in your own workflow.
- **Setup complexity:** Marketplace actions are the least code to write (just a workflow step with `uses:` and a few `with:` inputs) but trade that off against depending on a third party's maintenance of the underlying Puppeteer version, Node version, and Docker base image.
- **CI fit:** Since these bundle Puppeteer (and therefore Chromium) inside their own action Docker image/runtime, the Chromium download/install cost is hidden inside the action rather than an explicit workflow step — but it still happens on every run unless the action's own image caches it internally (not verifiable without inspecting each action's source/Dockerfile).

## 4. Lighter-weight alternatives (no full browser engine)

| Tool | License / cost | Renders JS? | Notes |
|---|---|---|---|
| wkhtmltopdf | Open source (LGPL) | No (WebKit render, no scripting engine beyond what's baked in) | See maintenance status below |
| WeasyPrint | Open source (BSD) | No | Python; strong CSS paged-media support |
| Pandoc (+ backend) | Open source (GPL) | Depends on backend | Pandoc itself is a converter, not a PDF renderer — it delegates |
| Prince XML | Commercial | No (CSS-driven, not JS) | Also usable as a Pandoc `--pdf-engine` |
| Hosted URL/HTML-to-PDF APIs | Mixed free tiers + paid | Varies by provider | Offloads the browser/engine entirely to a third-party service |

- **wkhtmltopdf:**
  - Uses a WebKit-based rendering engine with no live JavaScript execution loop for dynamic content (static HTML/CSS renders fine).
  - **Maintenance status is a real concern for a new project as of today:** per the project's own status page, the maintainer describes it as having "no deadline" for future work, notes the bundled WebKit hasn't been updated since 2012 and Qt 4 lost support in 2015, and that the planned 0.13 release "stalled" after 2017. The maintainer's own recommendation for new projects is to consider **WeasyPrint** (for controlled HTML reports), **Puppeteer** (for JS-heavy content), or commercial tools like **Prince** instead — [wkhtmltopdf.org/status.html](https://wkhtmltopdf.org/status.html).
  - Print stylesheet: same idea as browser-based tools — it renders whatever CSS/HTML it's given; a `@media print` stylesheet is optional but improves control.
  - CI fit: binary install (native package or downloaded binary) rather than an npm-installed browser; smaller than a full Chromium download, but you inherit the outdated-engine risk noted above.

- **WeasyPrint:**
  - Python package (`pip install weasyprint`), requiring Pango ≥ 1.44.0 as a core native dependency, plus supporting Python packages (pydyf, tinyhtml5, tinycss2, cssselect2, Pyphen, Pillow, fontTools) — [doc.courtbouillon.org/weasyprint/stable/first_steps.html](https://doc.courtbouillon.org/weasyprint/stable/first_steps.html).
  - Described by its own docs as "a visual rendering engine for HTML and CSS that can export to PDF," with its CSS layout engine "written in Python, designed for pagination" — [doc.courtbouillon.org/weasyprint/stable/](https://doc.courtbouillon.org/weasyprint/stable/).
  - No JavaScript execution — fine for a static CV page with no client-side rendering, but would not work if the site depends on JS to render final content.
  - Linux install is via distro package manager where available (Debian/Ubuntu/Fedora/Arch/Gentoo packages listed); Docker images and a Conda package are also offered, both relevant for CI — [doc.courtbouillon.org/weasyprint/stable/first_steps.html](https://doc.courtbouillon.org/weasyprint/stable/first_steps.html).
  - No download-size or browser-binary caching concerns the way Puppeteer/Playwright have — the install footprint is a Python package plus a few native libraries, generally lighter than a bundled Chromium.

- **Pandoc (+ backend engine):**
  - Pandoc itself is a document-format converter, not a PDF rendering engine — for PDF output it delegates to one of several **PDF engines**, selectable via `--pdf-engine`: `pdflatex`, `lualatex`, `xelatex`, `latexmk`, `tectonic`, `context`, `wkhtmltopdf`, `weasyprint`, `pagedjs-cli`, `prince`, `typst`, plus `groff`/`pdfroff` for roff output — [pandoc.org/MANUAL.html](https://pandoc.org/MANUAL.html).
  - Relevant to this project: HTML can be used as the intermediate representation with `weasyprint`, `prince`, or `wkhtmltopdf` as the actual PDF-producing backend, with a `--css` option to apply styling — [pandoc.org/MANUAL.html](https://pandoc.org/MANUAL.html). In other words, choosing "Pandoc" doesn't remove the need to also pick one of the other tools in this table as its backend; it mainly matters if the CV's source of truth were Markdown/structured text rather than the already-built HTML. Since this project already builds static HTML, Pandoc adds a conversion hop rather than replacing one.

- **Prince XML:**
  - Commercial software: purchase page lists a Desktop License at $495 one-time (single user), a Per-Server license at $3,800 one-time (non-commercial/government pricing, volume discounts at 5+ servers), an Academic Server license at $1,900 one-time, and a Commercial Site License described as an annual fee "starting around $2000 per year for startups" — [princexml.com/purchase](https://www.princexml.com/purchase/). No free-tier or trial detail was surfaced on the purchase page itself.
  - Renders HTML/XHTML/XML/SVG to PDF using CSS for layout (headers, footers, page numbers, tables, columns, footnotes), with export options like bookmarks, encryption, and font embedding — [princexml.com](https://www.princexml.com/).
  - Realistically a paid/commercial option, not typically justified for a personal CV site's CI pipeline unless already licensed for other reasons.

- **Hosted URL-to-PDF API services** (offload rendering to a third party over HTTP instead of running any engine yourself in CI):
  - **DocRaptor** — uses the commercial Prince engine under the hood ("We're the only API using the commercial Prince library to generate PDFs"); free usage is limited to unlimited *watermarked* test documents plus 5 non-watermarked conversions/month, with paid plans starting at $15/month for 125 documents — [docraptor.com/free-html-to-pdf-api](https://docraptor.com/free-html-to-pdf-api).
  - **PDFShift** and **API2PDF** were both reported (via aggregated search results, not each individually fetched from their own docs in this research) to offer free tiers around 50 credits/month with paid plans from roughly $9/month; API2PDF reportedly supports multiple backend engines (Chromium, wkhtmltopdf, LibreOffice) — general web search summary, treat as secondary-sourced and worth confirming directly on their own pricing pages before relying on it.
  - Fit for this project: removes the need to install any renderer in the CI job at all — a workflow step just POSTs the built HTML (or its public GitHub Pages URL, once deployed) to the API and downloads the resulting PDF — but introduces a dependency on an external paid/rate-limited service for a build step, and (for URL-based APIs) may require the site to already be live at a URL before the PDF step can run, complicating a single "build once, deploy once" pipeline.

---

## If I had to guess

Non-binding lean, not a recommendation: for a small personal static CV site already built via GitHub Actions, my guess is that **Playwright** (or equally Puppeteer — the two are very similar here) driving headless Chromium against the already-built local HTML file would end up being the path of least resistance, mainly because it needs no external paid service, no separate rendering engine ecosystem (Python/Pango, LaTeX, or a commercial license) alongside the existing Node/TypeScript toolchain, and its official docs are explicit and current about the one thing that trips people up in CI (`npx playwright install --with-deps`, and the explicit guidance not to bother caching the browser binary). The main added cost either way is authoring a `@media print` stylesheet so the PDF looks intentional rather than like a raw screenshot of the webpage — that's true of every browser-engine-based approach here, not specific to Playwright. This is a lean based on ecosystem fit for a beginner already using TypeScript/Node, not a claim that lighter-weight tools like WeasyPrint would be worse — that trade-off is exactly what the downstream ticket should weigh.
